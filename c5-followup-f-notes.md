# C5 follow-up F — Reset a forgotten password by emailed code (crew)

Prototype: one stack screen and two links in `c1-crew-shell.html` — the sign-in's **Forgot password?** (`employee-login-forgot`) and the Change password sheet's **Send me a code** (`crew-pw-forgot`) both open `#s-reset` (`crew-reset`). Deep links: `?screen=reset` (the email step), `?screen=reset&step=2` (the code step), `?screen=reset&from=profile` (the signed-in path). Checks: 28 of the 454 in `tools/test_c1.js` (`shots-f/f-*.png`, 390 × 844 and 360 × 800). Written 23 Oct 2026 after Josh: "changing password also needs to be done by email. like sending a code to the email and crew use that code to set a new pass."

Order: after C5 is built. It is small enough to ride with Follow-up D (the distance question + weather) in one round; if D slips, it goes alone. It touches `app/employee/login.tsx` and the C5 Profile sheet, so it must land after C5, not before.

## 1. Why

C5 gives the crew a Change password sheet that needs the **current** password. A crew member who has forgotten it has nothing: the crew sign-in has no "Forgot password?" (the admin sign-in has had one since Round 43), and the owner cannot set a crew password from the admin app either. Today the only way back in is the owner deleting and re-adding them. The admin side already has the mechanism (`routes/password_reset.py`: a hashed single-use token emailed as a link, 60 minutes, never says whether the email exists, rate-limited). The crew version uses the same pattern with a **6-digit code typed into the app** instead of a link, because the crew app is a phone app: a link in an email opens the browser, not the app, and a code is what tradies know from their bank.

## 2. What the crew member sees

**Sign in** (`app/employee/login.tsx`): a right-aligned **"Forgot password?"** link under the password field, above the Sign in button, 44 px tall. It opens the reset screen with the email already typed on the sign-in carried across.

**Reset your password** (`app/employee/reset-password.tsx`, a stack screen, back "Sign in"):

1. **Email step** (title "Reset your password"): the line *"We'll email you a code to set a new password."*, the **Email** field (`autocomplete="username"`), **Send me a code**. Empty or not an email → the field outlined red, one inline line *"Enter your email address."*. Tap → `POST /employees/forgot-password {email}` → always the code step, whatever the server knows (§3).
2. **Code step** (title "Check your email"): *"We sent a code to **{email}**. It lasts 15 minutes. If it isn't there, check your junk folder."*; **Code** (numeric keyboard, `autocomplete="one-time-code"` so iOS and Android offer the code from the email, max 6, placeholder "6-digit code"); **New password** with the hint *"At least 8 characters. You'll sign in with this from now on."*; **Set new password**; under it **Send another code** (left; posts forgot-password again, clears both fields) and **Wrong email?** (right; back to the email step). Client checks before the request: code not 6 digits → *"Enter the 6-digit code from your email."*; password under 8 → *"At least 8 characters."* (both can show at once, each under its field). The server's one refusal (§3) shows under the Code field: *"That code isn't right or has expired."*
3. **Done** (title "Password changed"; the back button is hidden, the one button below does the same): the green tick, *"Sign in with **{email}** and your new password."*, **Sign in** → the sign-in screen with the email filled, password empty.

**Profile › Change password** (the C5 sheet): a line under the password fields, *"Forgot your current password? **Send me a code**"*. Tap → the sheet closes, the app posts forgot-password with the signed-in account's email (the crew cannot change their email, so there is no email step) and lands on the **code step** with back "Profile", no "Wrong email?" link, Send another code kept. Done reads *"Your new password works from now on."* with **Back to Profile**. The signed-in session stays (it is the one that set the password); every other device is signed out where the backend records crew sessions (§3; today it does not).

No banner, no toast, no "we emailed you" pop-up: the code step is the confirmation. Nothing says whether the email exists (the admin rule; §3).

## 3. Backend

**New `routes/employee_password_reset.py`** (register in `server.py` next to `password_reset`), mirroring `routes/password_reset.py` line for line where it can:

- **`POST /employees/forgot-password {email}`**, no auth. `email = body.email.strip().lower()`; `db.employees.find_one({"email": {"$regex": f"^{re.escape(email)}$", "$options": "i"}, "deleted": {"$ne": True}})` (case-insensitive: `employee_login` matches the stored email as typed and a crew member stored with a capital letter would otherwise get no code) (crew email is unique across the platform: `employee_login` looks it up by email alone and the duplicate check in `create_employee`/`register` is global). When found: a 6-digit code from `secrets.randbelow(1_000_000)` zero-padded; store **only its sha256** in `employee_reset_codes` `{_id: uuid, employee_id, owner_admin_id, email, code_hash, attempts: 0, used: false, created_at, expires_at: now + 15 min}` after `delete_many({employee_id, used: false})` (one live code per crew member, so "Send another code" invalidates the first); email the code with `send_email(to=email, subject="Your Paint Trade HQ code", html=...)` when `email_configured()`, log only `ref=code_hash[:8]` as the admin route does, never the code; a send failure is logged, not returned. Not found, or deleted: do nothing. **Always `200 {"message": "If that email is on a crew, we've sent a code."}`** in the same time either way (do the hash even when not found, so timing does not reveal existence). The email body: the heading "Your code", the six digits in 32 px monospace, "It lasts 15 minutes. If you didn't ask for it, ignore this email — your password hasn't changed.", the business name is **not** in it (the platform sends it; a crew member can only be on one business anyway). Plain `<table>` HTML like `_reset_email_html`; no links, so `_assert_safe_email` has nothing to check (the phrase list in `services/email.py:72` does not match "enter the code in the app"; keep it that way, do not write "reply with the code").
- **`POST /employees/reset-password {email, code, new_password}`**, no auth. Look up the live code for that email (`{email, used: false}`); refuse with **400 `"That code isn't right or has expired."`** when there is none, it has expired, `attempts >= 5`, or the sha256 of the given code does not match (increment `attempts` on a mismatch; the same text for every case so nothing leaks which). `new_password` under 8 → 400 `"New password must be at least 8 characters."` (the admin's text). Success: `employees.update_one({_id}, {$set: {password_hash: hash_password(new_password), password_changed_at: now}})`, mark the code `used: true, used_at`, and call `revoke_all_other_sessions(admin_id=employee_id, keep_jti=<the bearer's jti only when the bearer verifies and its `sub` equals the matched employee's `_id`, else "">, owner_admin_id=employee.owner_admin_id, reason="password_reset")` (`services/sessions.py`, keyword-only; callable with an employee id). In the pre-Round-74 clone crew logins are **not** recorded in `admin_sessions` (`employee_login` never calls `services.sessions.create_session`; its only callers are the admin login and signup), so the call returns 0 and no crew device is signed out. Check `employee_login` in the live tree; if it still records nothing, make the call anyway (harmless), assert nothing about revocation in the tests, add no check to `auth.py` (not in the file list), and say in the report that crew devices are not signed out. When comparing `expires_at`, normalise a naive value to UTC first, as `password_reset.py:146–150` does. Return `{"ok": true}`.
- The bearer on reset-password is **optional** (`HTTPBearer(auto_error=False)`, the C5 video route pattern): the Profile path sends it so its own session is kept; the sign-in path has none.
- **Rate rules** in `rate_limiter.py`, directly after the two `^/api/admin/…-password/?$` entries, in `_RULES`'s own format: `(re.compile(r"^/api/employees/forgot-password/?$"), 5, 300, "ip"),` and `(re.compile(r"^/api/employees/reset-password/?$"), 10, 300, "ip"),`. Five attempts per code (above) is the second lock, so a 6-digit code cannot be brute-forced through many IPs.
- `C5`'s `PUT /employees/password` (current + new) stays; this round does not touch it.
- No admin route, no admin screen. The owner is not told; nothing is written to the owner's tenant except the crew member's own `password_hash` and `password_changed_at`.

**Decision: the one tick stays; no second "you have the right to store and use my details" tick.** Reasons, checked 23 Oct against the Acts and the OAIC's guidance (medium confidence: the session could not open legislation.gov.au and the OAIC site directly and read them through search extracts; **the lawyer confirms all of this**):
- What Australian privacy law asks for at collection is a plain **notice** (APP 5: what is collected, why, who sees it), not a consent tick; the OAIC says a Privacy Policy link is not that notice and recommends a short in-context notice in apps, which is what the facts card and the crew notice page are. A tick someone must give to continue is not valid consent anyway; consent is needed only for sensitive information (a police check), a use the person would not expect, or marketing, and then it is a separate, optional tick.
- The tick's job is the contract: the Terms' preamble already says ticking the box is acceptance, and register/finish record `agreed_to_terms`, `terms_version`, `terms_version_shown`, `terms_accepted_at` and `terms_accepted_ip`. (Lawyer: the IP is itself personal data and optional; keep or drop.)
- "We have a right to store and use your details" would contradict Terms §3 ("you own your data") and Privacy §1 (Paint Trade HQ stores it for the business), and reads as legalese.
- Work emails and texts (sign-in details, documents to sign, password codes, job messages) are not commercial messages under the Spam Act, so no consent or unsubscribe is needed for them; one promotional line or an "upgrade" footer in such an email would change that, so crew emails carry none. Marketing to crew, ever, gets its own optional opt-in.
- Keeping hours and pay records is the employer's own duty (Fair Work Act s 535, seven years); no consent involved.
- Location: Victoria's Surveillance Devices Act needs express or implied consent for a tracking device (whether a sign-in app on the worker's own phone counts is unsettled); NSW's Workplace Surveillance Act needs written notice before a new employee starts, saying the kind of surveillance, how, when it starts, whether continuous or intermittent, and whether ongoing, and forbids tracking off shift. The crew notice's Location paragraph is written to cover those points, and the app only records location at sign-in and sign-out. The lawyer confirms the notice satisfies NSW s 10 as the employer's written notice.
